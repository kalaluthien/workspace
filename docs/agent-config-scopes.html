Claude configuration lives in three scopes, and each file kind has one correct home. This pattern draws the shape — the scope matrix, the session composition, and the routing — so a reader can name the destination of any new instruction, rule, skill, agent, or memory without re-deriving the layout. The listings that filled the matrix are in the survey evidence appendix.

Session composition

The scopes are not alternatives — a session composes them. A session in a project entry loads the global instruction file, every ancestor CLAUDE.md down to its working directory, and the memory index of exactly one pool; rules from any scope fire later, when a matching file is read. Subagents inherit the same composition, snapshotted at session start (per the notes-pool memory reference-subagent-inheritance).

Routing logic locations

One rule holds throughout: the router for a thing lives one scope above the destinations it chooses between.

  1. Memory routing — ~/.claude/CLAUDE.md "Filing": the six routes in the figure above.
  2. Request routing — ~/workspace/.claude/CLAUDE.md, the project-entry table: route by intent, then read that entry's own documents first.
  3. Document routing — the same file, "Workspace layout": a document lands in docs/ with an agent- or service- plane prefix only when no project entry owns the topic.
  4. Survey routing — the same file, "Technical knowledge": read the wiki first; delegate any web survey to notes/ so the answer lands in the vault.
  5. Session routing — the workspace delegating skill: which herdr pane and repository a delegated session runs in.
  6. Pool self-description — each pool's MEMORY.md header restates its own boundary, so a reader inside the pool never needs the router.

Responsibility declarations

Each scope declares its own responsibility in the first lines of its CLAUDE.md, and the scope above assigns it — the two solid arrows in the first figure.

  • Global: ~/.claude/CLAUDE.md opens with "taste-level preferences that hold on any machine, in any repository" — the scope predicate itself.
  • Workspace: ~/workspace/.claude/CLAUDE.md opens by declaring the workspace a control plane over agents and services, and splits directories into workspace-owned and project entries. Its entry table assigns every project's responsibility from above.
  • Project: each entry's CLAUDE.md declares how to work inside the entry; the workspace table declares when to enter it. The two never repeat each other.
  • Memory pools: each MEMORY.md header carries the pool's charter — for example the workspace pool: "what coordinates more than one project or service and has no home in a repository".

What is not shown

The figures and the matrix claim placement and routing only. Not shown: the contents of any configuration file; the harness's load mechanics beyond the conditions the session figure names; settings.json, permissions, and hooks in every scope — the survey covers the five matrix file kinds and no more; and the history of retired scopes, which lives in the workspace pool's history-workspace-refactor memory.

Appendix: template connectivity check (2026-08-02)

The document templates are self-contained by decision, so their instructions connect only through explicit references. This check walks five author scenarios through the references that exist at commit 05f4c0d and records where a walk dead-ends. Each scenario starts where a real author starts — docs/README.md or a copied template — and follows only what the files themselves say.

scenariopath walkedverdict
Route a new document to its template README's chapter table carries a reader's-question column (why / what shape / how); the practice template's own example restates the same chooser in its first step — two independent paths connected
Add a document end to end README: "to add a document, follow the practice template's own example" — the example walks copy, fill, catalogue row, one commit connected
Resolve the cited research the templates and README cite seven notes/wiki/*.md pages by path; all seven exist in the notes vault connected
Add a figure to a practice or principle the figure discipline — C4 checklist, SVG conventions, figure CSS — lives only in pattern.html; practice.html says "a practice owes no figure" with no pointer, principle.html says nothing dead end
Warn in a pattern or principle the warning form — hazard, consequence, avoidance, placed at the step it names — and the .warning CSS live only in practice.html; the other two carry neither the rule nor a pointer dead end

Reading of the two dead ends: within its own genre every template is complete, but the shared component disciplines sit in exactly one sibling, and nothing routes an author there. This document is the evidence — its figures required opening pattern.html by hand and importing the figure CSS, a step no instruction named. The consistent fix is one pointer line in each template's header comment ("for a figure, follow pattern.html's checklist and copy its figure CSS; for a warning, practice.html's outline form"), keeping each rule written once while making every path to it explicit. The fix belongs to the template owners; this appendix only records the check.
