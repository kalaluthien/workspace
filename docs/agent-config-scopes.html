Prerequisites

  • The workspace is checked out at ~/workspace with its project entries in place (see ~/workspace/.claude/CLAUDE.md, "Workspace layout").
  • The global instruction file ~/.claude/CLAUDE.md exists; its "Filing" section is the taxonomy this survey reads the tree against.
  • Memory pools live under ~/.claude/projects/<encoded-cwd>/memory/, one pool per working directory — not inside any .claude/ directory.

Steps

  1. List the global scope. Only CLAUDE.md and rules/ hold content; skills/ and agents/ are empty by design, because machine-wide behavior lives in the instruction file and the conditional rules.

    $ ls ~/.claude/{CLAUDE.md,rules,skills,agents}
CLAUDE.md
rules/:  skill-authoring.md
skills/: (empty)
agents/: (empty)

  2. List the workspace scope. It adds the one cross-entry skill and the services-plane rule; it defines no agents.

    $ ls ~/workspace/.claude/{CLAUDE.md,rules,skills,output-styles}
CLAUDE.md
rules/:         services.md
skills/:        delegating/
output-styles/: simplified-technical.md

  3. List each project entry. Every entry carries its own CLAUDE.md; only notes/ defines skills and agents; no entry defines rules.

    $ for p in notes camera mabinogi-mobile-automation \
           claude-memory-viewer kalaluthien.github.io; do
    ls ~/workspace/$p/.claude/; done
notes/:      CLAUDE.md  skills/ (6)  agents/ (3)
camera/:     CLAUDE.md
mabinogi-mobile-automation/: CLAUDE.md
claude-memory-viewer/:       CLAUDE.md
kalaluthien.github.io/:      (no .claude — routed to _config.yml)

  4. List the memory pools. The global pool and the workspace pool map to the two upper scopes; four project pools exist.

    $ ls ~/.claude/projects/*/memory/

...-workspace-notes/:         MEMORY.md + 5 files

...-workspace-mabinogi-mobile-automation/: MEMORY.md + 1 file
...-workspace-claude-memory-viewer/:       MEMORY.md + 1 file

The three scopes divide cleanly: the global scope holds rules true anywhere, the workspace scope holds coordination across project entries, and each project entry holds only its own working knowledge. Every empty cell is deliberate.

Routing logic locations

One rule holds throughout: the router for a thing lives one scope above the destinations it chooses between.

  1. Memory routing — ~/.claude/CLAUDE.md "Filing": six numbered routes decide whether a takeaway becomes a global rule, an output-style rule, a setup-* memory, a workspace-pool procedure, a repository CLAUDE.md gotcha, or a repository docs/ truth.
  2. Request routing — ~/workspace/.claude/CLAUDE.md, the project-entry table: route by intent, then read that entry's own documents first.
  3. Document routing — the same file, "Workspace layout": a document lands in docs/ with an agent- or service- plane prefix only when no project entry owns the topic.
  4. Survey routing — the same file, "Technical knowledge": read the wiki first; delegate any web survey to notes/ so the answer lands in the vault.
  5. Session routing — the workspace delegating skill: which herdr pane and repository a delegated session runs in.
  6. Pool self-description — each pool's MEMORY.md header restates its own boundary, so a reader inside the pool never needs the router.

Responsibility declarations

Each scope declares its own responsibility in the first lines of its CLAUDE.md, and the scope above assigns it.

  • Global: ~/.claude/CLAUDE.md opens with "taste-level preferences that hold on any machine, in any repository" — the scope predicate itself.
  • Workspace: ~/workspace/.claude/CLAUDE.md opens by declaring the workspace a control plane over agents and services, and splits directories into workspace-owned and project entries. Its entry table assigns every project's responsibility from above.
  • Project: each entry's CLAUDE.md declares how to work inside the entry; the workspace table declares when to enter it. The two never repeat each other.
  • Memory pools: each MEMORY.md header carries the pool's charter — for example the workspace pool: "what coordinates more than one project or service and has no home in a repository".

The pattern across the whole survey: definitions and routers sit at global scope, assignments at workspace scope, instances at project scope. The one asymmetry worth knowing: the rule format is defined in a verified setup-* memory rather than a CLAUDE.md, because it is a harness behavior fact, not a preference.

Acceptance

Given any new configuration file — an instruction, a rule, a skill, an agent, a memory — the reader names its destination scope from the matrix and the routing list without re-deriving the layout. When the tree and this matrix disagree — a new project entry, a new rule file, a retired pool — re-run the four survey steps against the current tree and update this document in place.
