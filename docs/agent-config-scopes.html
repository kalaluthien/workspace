Each configuration kind files to the scope that matches how far its claim holds, and every router sits one scope above the destinations it chooses between.

Scope matrix

The scopes divide by how far a claim holds: the global scope carries what is true on any machine and in any repository, the workspace scope carries what coordinates the entries, and a project entry carries only its own working knowledge. Session composition

The scopes are not alternatives — a session composes them. It loads the global instruction file, every ancestor CLAUDE.md down to its working directory, and the memory index of exactly one pool, the one encoding that working directory. Rules from any scope stay dormant until the session reads a file their paths key matches, so a rule is the only configuration whose arrival depends on what the session opens. Subagents inherit the same composition, snapshotted at session start (per the global pool's setup-claude-subagents, verified 2026-07-16).

Router placement

Every scope declares its own predicate in the opening lines of its CLAUDE.md, and the scope above assigns it — the two governing edges in the first figure. The consequence is that no file decides its own home: the router for a thing always lives one scope above the destinations it chooses between, so a reader who knows what a thing is can find where it goes without opening any of the candidates.

The "Filing" section is the router for memories only. Four more routers exist, each one scope above what it chooses between:

  1. Request routing — the project-entry table in ~/workspace/.claude/CLAUDE.md: route by intent, then read that entry's own documents first.
  2. Document routing — the same file, "Workspace layout": a document lands in docs/ under an agent- or service- plane prefix only when no project entry owns the topic.
  3. Survey routing — the same file, "Technical knowledge": read the wiki first, and delegate any web survey to notes/ so the answer lands in the vault.
  4. Session routing — the workspace delegating skill: which herdr pane and repository a delegated session runs in.

Each memory pool also restates its own boundary in its MEMORY.md header, so a reader already inside a pool never has to climb back to the router to check whether a file belongs there.

Omissions

The figures and tables claim placement and routing, and nothing else. Not shown, deliberately:

  • The contents of any configuration file — the matrix names files and the kinds they hold, never what they say. Read the file.
  • Settings, permissions, and hooks — settings.json and settings.local.json exist at every scope and inside entries, and are filtered out of the third listing. They are configuration, but they are the harness's, not the instruction system's, and no "Filing" route mentions them.
  • The rest of ~/.claude/ — the runtime directories beside the instruction files (sessions, plugins, caches, history) hold no authored configuration.
  • Worktrees — ~/workspace/ also holds board-wt-trimsurfaces/, a git worktree of board/. It carries a .claude/CLAUDE.md because it is a checkout of the same repository, not because it is a sixth entry, and it is excluded from every count here.
  • Load mechanics — the second figure names the condition that selects each source, not the order, the token budget, or what happens when two scopes disagree.
  • History — which scopes and entries existed before today. That log is the workspace pool's history-workspace-refactor.
