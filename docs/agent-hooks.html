Answer

Conclusion
  1. 1Prompt in. Every prompt in every project picks up one line from UserPromptSubmit — a plain-language writing reminder, the only hook here that shapes the reply instead of checking something.
  2. 2Tool call. PreToolUse on Bash rewrites the command through rtk to cut output tokens, and PostToolUse on Write|Edit fails a backlog write whose items break the pool contract's grammar.
  3. 3Git layer. A git commit inside that Bash call leaves the harness entirely: all six repositories run the same no-main-commits guard, five then chain their own hook, and three of those check the workspace docs contract.
  4. 4Turn end. Stop blocks one stop per working turn with the Filing reminder — a turn that only answered in text is let straight through.

Layer ownership

Conclusion
  1. 1The trigger names the owner. A hook the session triggers — prompt, tool call, stop — is the harness's; a hook an index or a ref triggers is git's. No event fires both layers.
  2. 2One follows the operator, the other the clone. The four harness hooks sit in one file, ~/.claude/settings.json, and so apply in every repository this operator works; a git hook lives inside a clone, is never cloned, and fires for every actor — a peer agent, or the owner at a terminal — not only a Claude session.

Harness hooks

Conclusion
  1. 1Two guard the record, two guard the conduct. PostToolUse and Stop hold the memory pools' rules — the item grammar and the Filing pass; PreToolUse and UserPromptSubmit shape cost and register and refuse nothing.
  2. 2Stop asks twice over. It returns silently when stop_hook_active is set, so it can never loop a turn, and again when the finished turn made no tool call — a text-only answer has nothing to file.

Git hooks

Conclusion
  1. 1One guard, six repositories. Every clone runs the same file, ~/.claude/git-hooks/no-main-commits: it blocks a commit on main or master, passes a detached HEAD untouched, and prints the branch-or-worktree recipe.
  2. 2Five chain, one does not. Where a repository owns a pre-commit hook, core.hooksPath names .git/local-hooks, whose entry hook runs the guard first and the repository's own hook second; only kalaluthien.github.io still runs the guard alone.
  3. 3The docs contract now has callers. ~/workspace/scripts/check-docs is run by workspace, board, and camera on any commit that stages docs/; the other three ship no view it could check.
  4. 4One hook outside the chain. board also runs a reference-transaction hook, which starts one deploy per new version tag; it is installed in that same core.hooksPath directory, because the setting replaces .git/hooks rather than adding to it.

  1. Entry — installed hook. The short pre-commit git actually executes, reached because core.hooksPath names its directory.
  2. Shared guard — machine-wide check. no-main-commits, run first so no chained hook can be ordered ahead of it; a non-zero exit here ends the commit.
  3. Repo hook — repository check. The hook that repository would have run anyway, exec'd last, so its exit status is the commit's. In workspace and board the entry hook tests it for existence first, so a branch predating the file still commits; the other three exec it unconditionally.
Warning core.hooksPath replaces .git/hooks; it does not add to it, so setting it silently retires every hook still living there — a hooks directory git no longer reads is not an error, it is no hook at all. The trap this leaves behind is textual: an install line or a precondition that names .git/hooks reports a hook git will never call, so the check that should catch the absence is the thing asserting it is fine. Resolve git config core.hooksPath first and fall back to .git/hooks only when it is unset — which is what board/hooks/reference-transaction's install line and board/scripts/release-patch's precondition now both do, at board 044804c.
core.hooksPath must be absolute, or every hook silently stops running inside a linked worktree

Git resolves a relative core.hooksPath against the working directory. A linked worktree's own .git is a file, not a directory, so .git/local-hooks resolves to a path that does not exist there — and a missing hooks directory is not an error, it is no hook at all. Probed on git 2.54.0, 2026-08-06: with a relative value the entry hook fired in the main checkout and not in a git worktree add checkout of the same repository; setting the absolute value in the worktree restored it. All five configured repositories now hold the absolute form:

git config core.hooksPath "$PWD/.git/local-hooks"

Omissions

The figures and tables claim which hooks are installed, who owns each, and what each refuses; nothing else. Not shown, deliberately:

  • The pin's reach — the Commit field pins ~/workspace, which holds the shared checker and its own hooks/ but no other repository's: the harness hooks and the shared guard are tracked in ~/.claude at 13d1aa5, the chained hooks in their own repositories at board f3d4224 and camera d8741ec, and the entry hook under .git/local-hooks/ is version-controlled nowhere.
  • Inside the chained hooks — the last column of the repository table names what each adds in one line; the checks themselves belong to those repositories' own documents.
  • What check-docs checks — the six rules it applies and the contract block it parses are stated where the contract lives, docs/README.md; this view claims only who calls it and when.
  • The rtk rewrite — which commands rtk proxies, and by how much it trims them, is the tool's own fact (~/.claude/RTK.md), not this view's.
  • Other hook kinds — the walk covered .git/hooks/ and .git/local-hooks/ in the six repositories on 2026-08-06, samples excluded; the only hook file found outside the pre-commit chain was board's reference-transaction. Server-side hooks and CI checks are a different layer again.
  • Ordering across layers — the figure shows that a Bash call crosses into git, not how a harness hook and a git hook would interleave if both had something to say.
