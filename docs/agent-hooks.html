Answer

Four hooks fire inside the session itself, and a second layer — each repository's own git hooks — takes over the moment a session runs git commit.

  1. 1Prompt in. Every prompt in every project picks up one line from UserPromptSubmit.
    • The line is a plain-language writing reminder.
    • It is the only hook here that shapes the reply instead of checking something.
  2. 2Tool call. Two hooks wrap the tools a session runs.
    • PreToolUse on Bash rewrites the command through rtk to cut output tokens.
    • PostToolUse on Write|Edit fails a backlog write whose items break the pool contract's grammar.
  3. 3Git layer. A git commit inside that Bash call leaves the harness.
    • All six repositories run the same no-main-commits guard.
    • Five then chain their own hook.
    • Three of those check the workspace docs contract.
  4. 4Turn end. Stop blocks one stop per working turn with the Filing reminder.
    • A turn that only answered in text is let straight through.

Layer ownership

  1. 1The trigger names the owner. Whatever fires a hook says which layer owns it.
    • A hook the session triggers — prompt, tool call, stop — is the harness's.
    • A hook an index or a ref triggers is git's.
    • No event fires both layers.
  2. 2One follows the operator, the other the clone. The two layers travel differently.
    • The four harness hooks sit in one file, so they apply in every repository this operator works.
    • A git hook lives inside a clone and is never cloned.
    • It fires for every actor — a peer agent, or the owner at a terminal — not only a Claude session.

Untracked wiring is why the git layer is installed once per clone, not cloned with it
  • Harness side. Everything the harness runs is under version control.
    • No project settings file defines any hook.
    • ~/.claude tracks settings.json, hooks/, and git-hooks/.
  • Git side. The wiring itself is not under version control.
    • The entry point under .git/ and the core.hooksPath value are not tracked.
    • A fresh clone therefore starts with no chain until someone wires it.
  • The override is advertised. The guard's own refusal message names git commit --no-verify.

Harness hooks

  1. 1Two guard the record, two guard the conduct. Only half of the four can refuse anything.
    • PostToolUse and Stop hold the memory pools' rules — the item grammar and the Filing pass.
    • PreToolUse and UserPromptSubmit shape cost and register, and refuse nothing.
  2. 2Stop asks twice over. Two conditions send it back silently.
    • stop_hook_active is set, so the hook can never loop a turn.
    • The finished turn made no tool call — a text-only answer has nothing to file.

  • UserPromptSubmit guards the reply's register — plain, everyday language over jargon.
  • PreToolUse guards the token budget — the command is rewritten to its rtk proxy, which trims the output.
  • PostToolUse guards the backlog item grammar in any pool's backlog.md.
  • Stop guards the durable takeaway — the Filing reminder.
Both checking hooks fail loud: the offending line comes back, and an unreadable contract is a refusal
  • Backlog check. A rejected write comes back with the line that caused it.
    • It returns the offending line on stderr.
    • It refuses rather than passes when it cannot read the pool contract.
  • Stop check. It decides from the transcript, not from the last message.
    • It walks the transcript back to the last real user prompt.
    • It blocks the stop only if a tool call happened in between.

Git hooks

  1. 1One guard, six repositories. Every clone runs the same file, ~/.claude/git-hooks/no-main-commits.
    • It blocks a commit on main or master.
    • It passes a detached HEAD untouched.
    • It prints the branch-or-worktree recipe.
  2. 2Five chain, one does not. A repository that owns a pre-commit hook wires it behind the guard.
    • core.hooksPath names .git/local-hooks.
    • That entry hook runs the guard first and the repository's own hook second.
    • Only kalaluthien.github.io still runs the guard alone.
  3. 3The docs contract has callers. ~/workspace/scripts/check-docs runs from three of the chained hooks.
    • Workspace, board, and camera run it on any commit that stages docs/.
    • The other three ship no view it could check.
  4. 4One hook outside the chain. Board also runs a reference-transaction hook.
    • It starts one deploy per new version tag.
    • It sits in that same core.hooksPath directory, because the setting replaces .git/hooks rather than adding to it.

Two of the five entry hooks test for the repository hook first, so an old branch still commits

In workspace and board the entry hook checks that the repository's own hook exists before running it. A branch that predates the file therefore still commits. The other three exec it unconditionally.

Warning core.hooksPath replaces .git/hooks; it does not add to it.
  • Consequence: setting it silently retires every hook still living there.
    • A hooks directory git no longer reads is not an error — it is no hook at all.
  • Avoidance: resolve git config core.hooksPath first, and fall back to .git/hooks only when it is unset.
The trap this leaves is textual: a line naming .git/hooks reports a hook git will never call

An install line or a precondition written against .git/hooks asserts that the wiring is fine, so the check that should catch the absence is the thing hiding it. board/hooks/reference-transaction's install line and board/scripts/release-patch's precondition now both resolve the setting first, at board 044804c.

core.hooksPath must be absolute, or every hook silently stops running inside a linked worktree
  • Why it breaks. Git resolves a relative core.hooksPath against the working directory.
    • A linked worktree's own .git is a file, not a directory.
    • .git/local-hooks therefore resolves to a path that does not exist there.
    • A missing hooks directory is no hook at all.
  • The probe. Git 2.54.0, 2026-08-06.
    • With a relative value the entry hook fired in the main checkout and not in a git worktree add checkout of the same repository.
    • Setting the absolute value in the worktree restored it.
  • The fix, already applied. All five configured repositories now hold the absolute form.
git config core.hooksPath "$PWD/.git/local-hooks"

Omissions

The figures and tables claim which hooks are installed, who owns each, and what each refuses; nothing else. Not shown, deliberately:

  • The pin's reach — the Commit field pins ~/workspace only; the other trees are pinned per claim.
  • Inside the chained hooks — one line each in the table above; the checks belong to those repositories' own documents.
  • What check-docs checks — its rules live with the contract, in docs/README.md.
  • The rtk rewrite — which commands rtk proxies, and how much it trims, is the tool's own fact (~/.claude/RTK.md).
  • Other hook kinds — server-side hooks and CI checks are a different layer again.
  • Ordering across layers — how a harness hook and a git hook would interleave if both had something to say.
