Answer

Four hooks fire inside the session itself, and a second layer — each repository's own git hooks — takes over the moment a session runs git commit.

Conclusion
  1. 1Prompt in. Every prompt in every project picks up one line from UserPromptSubmit — a plain-language writing reminder, the only hook here that shapes the reply instead of checking something.
  2. 2Tool call. PreToolUse on Bash rewrites the command through rtk to cut output tokens. PostToolUse on Write|Edit fails a backlog write whose items break the pool contract's grammar.
  3. 3Git layer. A git commit inside that Bash call leaves the harness: all six repositories run the same no-main-commits guard, five then chain their own hook, and three of those check the workspace docs contract.
  4. 4Turn end. Stop blocks one stop per working turn with the Filing reminder. A turn that only answered in text is let straight through.

Layer ownership

Conclusion
  1. 1The trigger names the owner. A hook the session triggers — prompt, tool call, stop — is the harness's; a hook an index or a ref triggers is git's. No event fires both layers.
  2. 2One follows the operator, the other the clone. The four harness hooks sit in one file and so apply in every repository this operator works. A git hook lives inside a clone, is never cloned, and fires for every actor — a peer agent, or the owner at a terminal — not only a Claude session.

Harness hooks

Conclusion

  2. 2Stop asks twice over. It returns silently when stop_hook_active is set, so it can never loop a turn, and again when the finished turn made no tool call — a text-only answer has nothing to file.

  • Stop check. It walks the transcript back to the last real user prompt, and blocks the stop only if a tool call happened in between.

Git hooks

Conclusion
  1. 1One guard, six repositories. Every clone runs the same file, ~/.claude/git-hooks/no-main-commits: it blocks a commit on main or master, passes a detached HEAD untouched, and prints the branch-or-worktree recipe.
  2. 2Five chain, one does not. Where a repository owns a pre-commit hook, core.hooksPath names .git/local-hooks, whose entry hook runs the guard first and the repository's own hook second. Only kalaluthien.github.io still runs the guard alone.
  3. 3The docs contract has callers. ~/workspace/scripts/check-docs is run by workspace, board, and camera on any commit that stages docs/; the other three ship no view it could check.
  4. 4One hook outside the chain. board also runs a reference-transaction hook, which starts one deploy per new version tag. It sits in that same core.hooksPath directory, because the setting replaces .git/hooks rather than adding to it.

  1. Entry — installed hook. The short pre-commit git actually executes, reached because core.hooksPath names its directory.
  2. Shared guard — machine-wide check. no-main-commits, run first so no chained hook can be ordered ahead of it; a non-zero exit here ends the commit.
  3. Repo hook — repository check. The hook that repository would have run anyway, exec'd last, so its exit status is the commit's.
Two of the five entry hooks test for the repository hook first, so an old branch still commits

In workspace and board the entry hook checks that the repository's own hook exists before running it. A branch that predates the file therefore still commits. The other three exec it unconditionally.

Warning core.hooksPath replaces .git/hooks; it does not add to it.
  • Consequence: setting it silently retires every hook still living there, and a hooks directory git no longer reads is not an error — it is no hook at all.
  • Avoidance: resolve git config core.hooksPath first, and fall back to .git/hooks only when it is unset.
The trap this leaves is textual: a line naming .git/hooks reports a hook git will never call

An install line or a precondition written against .git/hooks asserts that the wiring is fine, so the check that should catch the absence is the thing hiding it. board/hooks/reference-transaction's install line and board/scripts/release-patch's precondition now both resolve the setting first, at board 044804c.

core.hooksPath must be absolute, or every hook silently stops running inside a linked worktree
  • Why it breaks. Git resolves a relative core.hooksPath against the working directory. A linked worktree's own .git is a file, not a directory, so .git/local-hooks resolves to a path that does not exist there — and a missing hooks directory is no hook at all.
  • The probe. Git 2.54.0, 2026-08-06: with a relative value the entry hook fired in the main checkout and not in a git worktree add checkout of the same repository. Setting the absolute value in the worktree restored it.
  • The fix, already applied. All five configured repositories now hold the absolute form.
git config core.hooksPath "$PWD/.git/local-hooks"

Omissions

The figures and tables claim which hooks are installed, who owns each, and what each refuses; nothing else. Not shown, deliberately:

  • The pin's reach — the Commit field pins ~/workspace only; the other trees are pinned per claim.
  • Inside the chained hooks — one line each in the table above; the checks belong to those repositories' own documents.
  • What check-docs checks — its rules live with the contract, in docs/README.md.
  • The rtk rewrite — which commands rtk proxies, and how much it trims, is the tool's own fact (~/.claude/RTK.md).
  • Other hook kinds — server-side hooks and CI checks are a different layer again.
  • Ordering across layers — how a harness hook and a git hook would interleave if both had something to say.
