Goal
A service reachable at https://<name>.<tailnet>.ts.net on its own tailnet node, installable on a phone beside every other service, with no handler left on the machine node.

One node per service — two ports on one node cannot both be installed as phone apps

A tailnet node carries exactly one *.ts.net name. There is no alias, MagicDNS accepts no custom record, and tailscale cert is bound to the node's own certificate domains, so a second name always means a second node. Publishing two services as two ports on one node looks equivalent and is not: Android matches an installed web app to a URL by scheme and host and ignores the port, so the app installed first claims the second service's URL, and the browser offers "open the other app" where the install entry belongs.

Prerequisites

  • colima running with the docker CLI, per the setup-colima memory in the global pool. The sidecar is a container like any other.
  • The service already answering on a host loopback port — for example 127.0.0.1:8300. The sidecar publishes an existing port; it does not start the service.
  • MagicDNS and HTTPS certificates enabled for the tailnet, per notes/wiki/tailscale.md. Without them the node hangs on certificate provisioning.
  • A Tailscale auth key that is reusable and not ephemeral, saved at ~/.config/ts-sidecar/authkey with mode 600. An ephemeral key deletes the device when it goes offline, which destroys the identity the node exists to hold. Only the user creates this; an agent never prints it or puts it on a command line.

Steps

  1. Name the node after the service and write its serve configuration. The name becomes the hostname, so it takes the service's name, not the machine's; the configuration points at the loopback port the service already answers on.

    app=board          # → board.<tailnet>.ts.net
port=8300          # the service's existing host port

mkdir -p ~/.config/ts-sidecar/$app
cat > ~/.config/ts-sidecar/$app/serve.json <<JSON
{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "\${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://host.docker.internal:$port" } }
    }
  }
}
JSON

    The ${TS_CERT_DOMAIN} placeholder is substituted by the container at startup.

    notice host.docker.internal is what reaches a macOS loopback-only bind under colima. --network host means the Linux VM and would not reach the service.

  2. Start the sidecar node as a container of its own.

    docker run -d --name "ts-$app" --restart unless-stopped \
  -v "$HOME/.local/state/ts-$app:/var/lib/tailscale" \
  -v "$HOME/.config/ts-sidecar:/config:ro" \
  -e TS_AUTHKEY="file:/config/authkey" \
  -e TS_AUTH_ONCE=true \
  -e TS_HOSTNAME="$app" \
  -e TS_STATE_DIR=/var/lib/tailscale \
  -e TS_SERVE_CONFIG="/config/$app/serve.json" \
  tailscale/tailscale:stable
    warning Omitting TS_STATE_DIR makes the container pass --state=mem:.
    • Consequence: the node registers as ephemeral, so the control plane deletes it when the container stops and the replacement can take the name <name>-1 permanently. The same directory holds the TLS certificates, so the node also re-issues from Let's Encrypt on every restart.
    • Avoidance: set TS_STATE_DIR and bind-mount a host directory onto it, both as shown above.
    notice Two variable names people reach for do not exist: TS_AUTHKEY_FILE and TS_SERVE_PORT. The real mechanisms are the file: prefix on the TS_AUTHKEY value and TS_SERVE_CONFIG. Mount the directory holding serve.json, never the file: the watch is on the directory.

  3. Verify the new hostname answers before changing anything else. The first certificate takes up to a minute.

    docker logs "ts-$app" | tail -20
tailscale status | grep "$app"
curl -sI "https://$app.$(tailscale status --json | /usr/bin/python3 -c \
  'import json,sys; print(json.load(sys.stdin)["Self"]["DNSName"].rstrip(".").split(".", 1)[1])')/" | head -1

    A working run prints HTTP/2 200, and a status line whose name is exactly the one chosen, with no -1 suffix.

  4. Move the service's own host settings onto the node name. Two kinds exist, and both bind a hostname that has just changed.

    • An allowlist of accepted Host headers. Derive it from the node name plus the tailnet suffix, never from the machine node's own FQDN — reading Self.DNSName whole re-pins the retired name and answers 400 to every phone request. The value belongs in the service's own launch path, not in a shell one-off, or the next deploy undoes it (.claude/rules/services.md).
    • An identity gate. It keeps working: the proxy now arrives from a container rather than the host loopback, but the tailnet identity of the requesting device still reaches the service. Verified 2026-08-02 by sending a message through Collie's phone app across its sidecar with its trusted-user setting unchanged.

    Where each setting lives differs per service, so this walk records no single command for it.

  5. Retire the old mount on the machine node, one port at a time, and only once the new hostname answers 200.

    tailscale serve --https=8443 off
tailscale serve status

    tailscale serve status then reports no configuration for that port.

    warning tailscale serve reset is never the way to turn a mount off.
    • Consequence: it removes every handler on the host, including other services'.
    • Avoidance: name the one port, as above.

  6. Restart the container to prove the identity survives, which is what the state volume is for.

    docker restart "ts-$app"
tailscale status | grep "$app"

    The name comes back unchanged.

  7. Reinstall the app on the phone from the new URL. An installed web app belongs to its origin, so the old install is a different app and will not follow the move.

Acceptance

Each service answers 200 at its own https://<name>.<tailnet>.ts.net, tailscale serve status on the machine node reports no configuration for them, both nodes keep their names across a container restart, and each app installs from the phone on its own — the outcome a shared hostname made impossible.

Recovery

The failure modes this procedure records, with what each looks like and the way back. The record does not mark which of them the walk itself hit.

  • 400 instead of 200, most often after a service redeploy, while the node itself is up and correctly named: the service's own host allowlist has fallen back to the machine FQDN. Fix the derivation in the service's launch script — node name plus tailnet suffix — and redeploy. Setting it by hand works until the next deploy repeats the failure.
  • No response at all from the new hostname: the certificate is still being issued, or the tailnet lacks HTTPS certificates. Wait out the first minute, then enable HTTPS certificates for the tailnet.
  • The name comes back with a -1 suffix after docker restart: the state directory is not persisted, and the hostname every installed app was built against has just moved. This walk records the recognition only — no way back from a taken -1 name is recorded.
  • A check fails right after a mount is retired: restore the mount that was just removed and stop, rather than retiring the next port. This walk records no command for restoring a removed mount.
