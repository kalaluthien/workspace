Giving a service its own tailnet hostname

Category
practice
Goal
A service reachable at https://<name>.<tailnet>.ts.net on its own tailnet node, installable on a phone beside every other service, with no handler left on the machine node.

Prerequisites

  • colima running with the docker CLI, per the setup-colima memory in the global pool. The sidecar is a container like any other.
  • The service already answering on a host loopback port — for example 127.0.0.1:8300. The sidecar publishes an existing port; it does not start the service.
  • MagicDNS and HTTPS certificates enabled for the tailnet, per notes/wiki/tailscale.md. Without them the node hangs on certificate provisioning.
  • A Tailscale auth key that is reusable and not ephemeral, saved at ~/.config/ts-sidecar/authkey with mode 600. An ephemeral key deletes the device when it goes offline, which destroys the identity the node exists to hold. Only the user creates this; an agent never prints it or puts it on a command line.

Why a node rather than a port

A tailnet node carries exactly one *.ts.net name. There is no alias, MagicDNS accepts no custom record, and tailscale cert is bound to the node's own certificate domains, so a second name always means a second node. Publishing two services as two ports on one node looks equivalent and is not: Android matches an installed web app to a URL by scheme and host and ignores the port, so the app installed first claims the second service's URL, and the browser offers "open the other app" where the install entry belongs. One node per service is what makes both installable.

Steps

  1. Choose the node name — it becomes the hostname, so name it after the service, not after the machine. Write the serve configuration for it, pointing at the loopback port the service already answers on.

    app=board          # → board.<tailnet>.ts.net
port=8300          # the service's existing host port

mkdir -p ~/.config/ts-sidecar/$app
cat > ~/.config/ts-sidecar/$app/serve.json <<JSON
{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "\${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://host.docker.internal:$port" } }
    }
  }
}
JSON

    host.docker.internal reaches a macOS loopback-only bind under colima; --network host would mean the Linux VM and would not. The ${TS_CERT_DOMAIN} placeholder is substituted by the container at startup.

  2. Start the sidecar node.

    docker run -d --name "ts-$app" --restart unless-stopped \
  -v "$HOME/.local/state/ts-$app:/var/lib/tailscale" \
  -v "$HOME/.config/ts-sidecar:/config:ro" \
  -e TS_AUTHKEY="file:/config/authkey" \
  -e TS_AUTH_ONCE=true \
  -e TS_HOSTNAME="$app" \
  -e TS_STATE_DIR=/var/lib/tailscale \
  -e TS_SERVE_CONFIG="/config/$app/serve.json" \
  tailscale/tailscale:stable

    TS_STATE_DIR is not optional. Omitting it makes the container pass --state=mem:, which registers the node as ephemeral: the control plane deletes it when it stops, and the replacement can take the name <name>-1 permanently. The same directory holds the TLS certificates, so losing it also re-issues from Let's Encrypt on every restart.

    Two variable names people reach for do not exist: TS_AUTHKEY_FILE and TS_SERVE_PORT. The real mechanisms are the file: prefix on the TS_AUTHKEY value and TS_SERVE_CONFIG. Mount the directory holding serve.json, never the file: the watch is on the directory.

  3. Verify the node before changing anything else. The first certificate takes up to a minute.

    docker logs "ts-$app" | tail -20
tailscale status | grep "$app"
curl -sI "https://$app.$(tailscale status --json | /usr/bin/python3 -c \
  'import json,sys; print(json.load(sys.stdin)["Self"]["DNSName"].rstrip(".").split(".", 1)[1])')/" | head -1

    A working run prints HTTP/2 200 and a status line whose name is exactly the one chosen, with no -1 suffix.

    • 400 instead of 200: the service has its own host allowlist and still accepts only the old name. Move it to the node name and redeploy the service — see "Move the service's own host settings" below.
    • No response at all: the certificate is still being issued, or the tailnet lacks HTTPS certificates.

  4. Move the service's own host settings. Two kinds exist, and both bind a hostname that has just changed.

    • An allowlist of accepted Host headers. Derive it from the node name plus the tailnet suffix, never from the machine node's own FQDN — reading Self.DNSName whole re-pins the retired name and answers 400 to every phone request.
    • An identity gate. It keeps working: the proxy now arrives from a container rather than the host loopback, but the tailnet identity of the requesting device still reaches the service. Verified 2026-08-02 by sending a message through Collie's phone app across its sidecar with its trusted-user setting unchanged.

  5. Retire the old mount on the machine node, one port at a time, and only once the new hostname answers 200.

    tailscale serve --https=8443 off
tailscale serve status

    Never tailscale serve reset — it removes every handler on the host, including other services'. If a check fails, restore the mount that was just removed and stop.

  6. Prove the identity survives a restart, which is what the state volume is for.

    docker restart "ts-$app"
tailscale status | grep "$app"

    The name must come back unchanged. A -1 suffix means the state directory is not persisted, and the hostname every installed app was built against has just moved.

  7. Reinstall the app on the phone from the new URL. An installed web app belongs to its origin, so the old install is a different app and will not follow the move.

Acceptance

Each service answers 200 at its own https://<name>.<tailnet>.ts.net, tailscale serve status on the machine node reports no configuration for them, both nodes keep their names across a container restart, and each app installs from the phone on its own — the outcome a shared hostname made impossible. When one of them 400s after a service redeploy, its host allowlist has fallen back to the machine FQDN; fix the derivation in the service's own launch script rather than by hand, or the next deploy repeats it.
