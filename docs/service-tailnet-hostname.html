Tailnet hostname

Doctype
guide
Goal
A service reachable at https://<name>.<tailnet>.ts.net on its own tailnet node, installable on a phone beside every other service, with no handler left on the machine node.
Updated
2026-08-16
Commit

Answer

  1. 1 One helper per service. A tailscale/tailscale container — a sidecar — runs beside the service as its own node on the tailnet.
    • It holds the hostname and passes :443 to the port the service already listens on.
    • It publishes the service, it never starts it.
  2. 2 Verify, then retire. The order of the two moves is fixed.
    • The new hostname must answer HTTP/2 200 first.
    • The machine node's old handler then comes off, one named port at a time.
  3. 3 Two things follow the node. Two settings outside the container move with it.
    • The hostname setting inside the service moves into its launch path.
    • The phone app is reinstalled from the new URL.

Sidecar node tailnet node

is
a tailscale/tailscale container beside one service, its own device on the tailnet
hostname
one <name>.<tailnet>.ts.net, taken from TS_HOSTNAME, with no alias and no custom MagicDNS record
serves
:443, proxied to the service's host port by the serve.json that TS_SERVE_CONFIG names
after
answers HTTP/2 200, and the phone installs the service from it as its own app
not
not a supervisor: it publishes the service and never starts it

Machine node tailnet node

is
the Mac itself, one device that every service on it would otherwise share
hostname
the machine's own FQDN, one name for every service published on it
serves
tailscale serve --https=<port> handlers, turned off one named port at a time
after
reports no configuration for the retired port
not
not a per-service name: a second service collides in the name, and the phone installs only the first

Prerequisites

  • A container runtime. colima running, with the docker CLI on the path.
    • This machine's own colima facts are in the setup-service-runtime memory.
  • A listening service. The service already answers on a host loopback port, such as 127.0.0.1:8300.
  • A tailnet that resolves and certifies. MagicDNS and HTTPS certificates are on for the tailnet.
    • Both are set in the admin console.
    • The concept page is notes/wiki/tailscale.md.
  • An auth key that outlives a restart. A reusable, non-ephemeral key, written by the owner.
    • It sits at ~/.config/ts-sidecar/authkey, mode 600.
An ephemeral auth key destroys the identity the node exists to hold

Tailscale deletes an ephemeral device when it goes offline, so the node loses its name and its certificates every time the container stops.

Steps

  1. Name the node after the service and write its serve configuration. The name becomes the hostname.

    app=board          # → board.<tailnet>.ts.net
port=8300          # the service's existing host port
tailnet=…          # the tailnet's MagicDNS suffix, as on any existing node

mkdir -p ~/.config/ts-sidecar/$app
cat > ~/.config/ts-sidecar/$app/serve.json <<JSON
{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "\${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://host.docker.internal:$port" } }
    }
  }
}
JSON
    notice --network host would put the proxy in the Linux VM, not on the Mac, where a 127.0.0.1-only bind is unreachable.
    A second service needs a second node, never a second port — the collision is in the name
    • One name per node. A node carries one *.ts.net name.
      • It takes no alias and no custom MagicDNS record.
      • tailscale cert is bound to the node's own domains.
    • The phone ignores the port. Android matches an installed web app by scheme and host.
      • The app installed first claims the second service's URL.
      • An installed app on :443 claimed a second service on :8443, and Chrome offered "open" in the menu slot where "install app" belongs.

  2. Start the sidecar node as a container of its own. The run prints the container id and nothing else.

    docker run -d --name "ts-$app" --restart unless-stopped \
  -v "$HOME/.local/state/ts-$app:/var/lib/tailscale" \
  -v "$HOME/.config/ts-sidecar:/config:ro" \
  -e TS_AUTHKEY="file:/config/authkey" \
  -e TS_AUTH_ONCE=true \
  -e TS_HOSTNAME="$app" \
  -e TS_STATE_DIR=/var/lib/tailscale \
  -e TS_SERVE_CONFIG="/config/$app/serve.json" \
  tailscale/tailscale:stable
    warning Omitting TS_STATE_DIR makes the container pass --state=mem:.
    • Consequence: the node registers as ephemeral.
      • It is deleted when the container stops, and the replacement can hold <name>-1 for good.
      • The certificates go with it, so every restart re-issues from Let's Encrypt into the duplicate-certificate limit, which resets about once per 34 hours.
    • Avoidance: set it and bind-mount a host directory onto it, as shown above.
    TS_AUTHKEY_FILE and TS_SERVE_PORT do not exist — the real mechanisms are already in the command
    • TS_AUTHKEY reads a file. A file: prefix on its value reads the key from a path.
    • TS_SERVE_CONFIG is the only serve mechanism. The mount is the directory holding serve.json rather than the file.
      • The watch is on the directory.
      • A bind-mounted file's inode is replaced on edit.

  3. Verify the new hostname answers before changing anything else. The first certificate can take up to a minute.

    docker logs "ts-$app" | tail -20
tailscale status | grep "$app"
curl -sI "https://$app.$tailnet.ts.net/" | head -1

    A working run prints HTTP/2 200, and the status line carries exactly the chosen name with no -1 suffix.

  4. Move the service's own hostname setting onto the node name, derived from that name plus the tailnet suffix. Where the setting lives differs per service. The step is done when the service still answers at the new hostname after a redeploy.

    warning Setting the value by hand in a shell instead of in the launch path.
    • Consequence: the next deploy restores the old hostname and the service answers 400 at the new origin.
    • Avoidance: edit the launch script or its configuration file, then redeploy.
    An identity gate keeps working across the move, verified 2026-08-02

    The proxy now arrives from a container rather than the host loopback, yet the tailnet identity of the requesting device still reaches the service. A message sent through Collie's phone app across its sidecar was accepted with the trusted-user setting unchanged.

  5. Retire the old handler on the machine node, one port at a time, once the new hostname answers 200.

    tailscale serve --https=8443 off
tailscale serve status

    The status output then reports no configuration for that port.

    warning tailscale serve reset is never the way to turn a handler off.
    • Consequence: it removes every handler on the host, other services' included.
    • Avoidance: name the one port, as above.

  6. Restart the container to prove the identity survives.

    docker restart "ts-$app"
tailscale status | grep "$app"

    The name comes back unchanged.

  7. Reinstall the app on the phone: uninstall the old one, then install from https://<name>.<tailnet>.ts.net. The phone then lists the service as its own app.

    The old install does not follow the move — to the phone, a new origin is a new app

    Android matches an installed web app by scheme and host, so the app installed from the old hostname keeps pointing at the old origin.

Acceptance

  1. 1 Its own name. Two checks, one on each node.
    • Each service answers HTTP/2 200 at https://<name>.<tailnet>.ts.net.
    • The machine node reports no configuration for the retired port.
  2. 2 Its own identity. Every name survives a container restart with no -1 suffix.
  3. 3 Its own app. Each service installs on the phone on its own, from its own hostname.

Recovery

gap The walk kept no per-step failure record, so "not recorded" below marks a hole in the record, not a failure that did not happen.
  • 400 rather than 200. The node is up and correctly named. The symptom usually follows a redeploy.
    • Cause: the service's host allowlist fell back to the machine node's own FQDN.
    • Way back: fix the derivation in the launch script and redeploy. A hand-set value fails again next deploy.
  • No response at all from the new hostname.
    • Cause: the certificate is still issuing, or the tailnet lacks HTTPS certificates.
    • Way back: wait out the first minute, then enable HTTPS certificates.
  • A -1 suffix on the name after docker restart.
    • Cause: the state directory is not persisted.
    • Way back: not recorded — the recognition only.
  • A check fails right after a handler is retired.
    • Cause: not recorded.
    • Way back: restore that handler and stop rather than retiring the next port. No restore command is recorded.
