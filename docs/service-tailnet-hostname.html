Tailnet hostname

Doctype
guide
Goal
A service reachable at https://<name>.<tailnet>.ts.net on its own tailnet node, installable on a phone beside every other service, with no handler left on the machine node.
Updated
2026-08-05
Commit

Answer

conclusion

1 · One node per service. A node carries exactly one *.ts.net name, and a phone matches an installed web app by scheme and host while ignoring the port, so a second service needs a second node, never a second port.

2 · A sidecar container is that node. One tailscale/tailscale container per service holds the name and proxies :443 to the service's existing host port; it publishes the service, it never starts it.

3 · Verify before retiring. The new hostname must answer HTTP/2 200 before the machine node's old mount comes off, one named port at a time — tailscale serve reset wipes every other service's handler with it.

4 · The node is not the last step. The service's own hostname setting moves into its launch path, and the phone app is reinstalled from the new URL, because an installed app belongs to the origin it was installed from.

Two ports on one node cannot both be installed as phone apps — the collision is in the name, not the port

A node carries one *.ts.net name with no alias and no custom MagicDNS record, and tailscale cert is bound to the node's own domains. Android matches an installed web app by scheme and host and ignores the port, so the app installed first claims the second service's URL — an installed app on :443 claimed a second service on :8443, and Chrome offered "open" in the menu slot where "install app" belongs.

Prerequisites

  • colima running with the docker CLI, per the setup-colima memory.
  • The service already answering on a host loopback port such as 127.0.0.1:8300 — the sidecar publishes it, never starts it.
  • MagicDNS and HTTPS certificates enabled for the tailnet in the admin console — a tailnet-level setting, not a container variable, per notes/wiki/tailscale.md.
  • A reusable, non-ephemeral auth key written by the owner to ~/.config/ts-sidecar/authkey, mode 600 — an ephemeral key deletes the identity the node exists to hold.

Steps

  1. Name the node after the service and write its serve configuration, since the name becomes the hostname.

    app=board          # → board.<tailnet>.ts.net
port=8300          # the service's existing host port
tailnet=…          # the tailnet's MagicDNS suffix, as on any existing node

mkdir -p ~/.config/ts-sidecar/$app
cat > ~/.config/ts-sidecar/$app/serve.json <<JSON
{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "\${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://host.docker.internal:$port" } }
    }
  }
}
JSON
    notice --network host would place the proxy in the Linux VM rather than on the Mac, and from there a 127.0.0.1-only bind is unreachable.

  2. Start the sidecar node as a container of its own; the run prints the container id and nothing else.

    docker run -d --name "ts-$app" --restart unless-stopped \
  -v "$HOME/.local/state/ts-$app:/var/lib/tailscale" \
  -v "$HOME/.config/ts-sidecar:/config:ro" \
  -e TS_AUTHKEY="file:/config/authkey" \
  -e TS_AUTH_ONCE=true \
  -e TS_HOSTNAME="$app" \
  -e TS_STATE_DIR=/var/lib/tailscale \
  -e TS_SERVE_CONFIG="/config/$app/serve.json" \
  tailscale/tailscale:stable
    warning Omitting TS_STATE_DIR makes the container pass --state=mem:.
    • Consequence: the node registers as ephemeral, so it is deleted when the container stops and the replacement can hold <name>-1 permanently; the certificates live there too, so every restart re-issues from Let's Encrypt into the duplicate-certificate limit, which resets at about one per 34 hours.
    • Avoidance: set it and bind-mount a host directory onto it, both as shown above.
    TS_AUTHKEY_FILE and TS_SERVE_PORT do not exist — the real mechanisms are already in the command

    A file: prefix on the TS_AUTHKEY value reads the key from a path, TS_SERVE_CONFIG is the only serve mechanism, and the mount is the directory holding serve.json rather than the file, because the watch is on the directory and a bind-mounted file's inode is replaced on edit.

  3. Verify the new hostname answers before changing anything else, allowing up to a minute for the first certificate.

    docker logs "ts-$app" | tail -20
tailscale status | grep "$app"
curl -sI "https://$app.$tailnet.ts.net/" | head -1

    A working run prints HTTP/2 200 and a status line carrying exactly the chosen name, with no -1 suffix.

  4. Move the service's own hostname setting onto the node name, deriving it from that name plus the tailnet suffix, or the service rejects requests arriving at the new origin.

    Where the setting lives differs per service, so the move is done when the derived value sits in the service's launch path rather than in a shell one-off the next deploy undoes.

    An identity gate keeps working across the move, verified 2026-08-02

    The proxy now arrives from a container rather than the host loopback, yet the tailnet identity of the requesting device still reaches the service: a message sent through Collie's phone app across its sidecar was accepted with the trusted-user setting unchanged.

  5. Retire the old mount on the machine node, one port at a time, and only once the new hostname answers 200.

    tailscale serve --https=8443 off
tailscale serve status

    The status output then reports no configuration for that port.

    warning tailscale serve reset is never the way to turn a mount off.
    • Consequence: it removes every handler on the host, including other services'.
    • Avoidance: name the one port, as above.

  6. Restart the container to prove the identity survives.

    docker restart "ts-$app"
tailscale status | grep "$app"

    The name comes back unchanged.

  7. Reinstall the app on the phone from the new URL, because an installed web app belongs to its origin and the old install is a different app that will not follow the move.

Acceptance

conclusion

1 · Its own name. Each service answers HTTP/2 200 at https://<name>.<tailnet>.ts.net, and the machine node reports no configuration for the retired port.

2 · Its own identity. Both names come back from a container restart with no -1 suffix.

3 · Its own app. Each service installs on the phone on its own, from its own hostname.
