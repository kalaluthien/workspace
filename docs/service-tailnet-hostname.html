Tailnet hostname

Doctype
guide
Goal
A service reachable at https://<name>.<tailnet>.ts.net on its own tailnet node, installable on a phone beside every other service, with no handler left on the machine node.
Updated
2026-08-04
Commit
3e3d22f
One node per service — two ports on one node cannot both be installed as phone apps

A node carries exactly one *.ts.net name: no alias, no custom MagicDNS record, and tailscale cert is bound to the node's own domains. Android matches an installed web app by scheme and host while ignoring the port, so the app installed first claims the second service's URL.

Prerequisites

  • colima running with the docker CLI, per the setup-colima memory.
  • The service already answering on a host loopback port such as 127.0.0.1:8300 — the sidecar publishes it, never starts it.
  • MagicDNS and HTTPS certificates enabled for the tailnet, per notes/wiki/tailscale.md, or the node hangs on certificate provisioning.
  • A reusable, non-ephemeral auth key written by the owner to ~/.config/ts-sidecar/authkey, mode 600 — an ephemeral key deletes the identity the node exists to hold.

Steps

  1. Name the node after the service and write its serve configuration, since the name becomes the hostname.

    app=board          # → board.<tailnet>.ts.net
port=8300          # the service's existing host port

mkdir -p ~/.config/ts-sidecar/$app
cat > ~/.config/ts-sidecar/$app/serve.json <<JSON
{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "\${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://host.docker.internal:$port" } }
    }
  }
}
JSON
    notice host.docker.internal is what reaches a macOS loopback-only bind under colima; --network host means the Linux VM and would not reach the service.

  2. Start the sidecar node as a container of its own; the run prints the container id and nothing else.

    docker run -d --name "ts-$app" --restart unless-stopped \
  -v "$HOME/.local/state/ts-$app:/var/lib/tailscale" \
  -v "$HOME/.config/ts-sidecar:/config:ro" \
  -e TS_AUTHKEY="file:/config/authkey" \
  -e TS_AUTH_ONCE=true \
  -e TS_HOSTNAME="$app" \
  -e TS_STATE_DIR=/var/lib/tailscale \
  -e TS_SERVE_CONFIG="/config/$app/serve.json" \
  tailscale/tailscale:stable
    warning Omitting TS_STATE_DIR makes the container pass --state=mem:.
    • Consequence: the node registers as ephemeral, so it is deleted when the container stops and the replacement can hold <name>-1 permanently; the certificates live there too, so every restart re-issues from Let's Encrypt.
    • Avoidance: set it and bind-mount a host directory onto it, both as shown above.
    TS_AUTHKEY_FILE and TS_SERVE_PORT do not exist — the real mechanisms are already in the command

    A file: prefix on the TS_AUTHKEY value reads the key from a path, TS_SERVE_CONFIG is the only serve mechanism, and the mount is the directory holding serve.json rather than the file, because the watch is on the directory.

  3. Verify the new hostname answers before changing anything else, allowing up to a minute for the first certificate.

    docker logs "ts-$app" | tail -20
tailscale status | grep "$app"
curl -sI "https://$app.$(tailscale status --json | /usr/bin/python3 -c \
  'import json,sys; print(json.load(sys.stdin)["Self"]["DNSName"].rstrip(".").split(".", 1)[1])')/" | head -1

    A working run prints HTTP/2 200 and a status line carrying exactly the chosen name, with no -1 suffix.

  4. Move the service's Host-header allowlist onto the node name, deriving it from that name plus the tailnet suffix — the machine node's Self.DNSName re-pins the retired name and answers 400 to every phone request.

    Where the setting lives differs per service, so the move is done when the derived value sits in the service's launch path rather than in a shell one-off the next deploy undoes.

    An identity gate keeps working across the move, verified 2026-08-02

    The proxy now arrives from a container rather than the host loopback, yet the tailnet identity of the requesting device still reaches the service: a message sent through Collie's phone app across its sidecar was accepted with the trusted-user setting unchanged.

  5. Retire the old mount on the machine node, one port at a time, and only once the new hostname answers 200.

    tailscale serve --https=8443 off
tailscale serve status

    The status output then reports no configuration for that port.

    warning tailscale serve reset is never the way to turn a mount off.
    • Consequence: it removes every handler on the host, including other services'.
    • Avoidance: name the one port, as above.

  6. Restart the container to prove the identity survives.

    docker restart "ts-$app"
tailscale status | grep "$app"

    The name comes back unchanged.

  7. Reinstall the app on the phone from the new URL, because an installed web app belongs to its origin and the old install is a different app that will not follow the move.

Acceptance

Each service answers 200 at its own https://<name>.<tailnet>.ts.net, the machine node's tailscale serve status reports no configuration for it, both names survive a container restart, and each app installs from the phone on its own.

Recovery

The record does not mark which of these the walk itself hit, and a cell reading "not recorded" is a gap in the record rather than an absent failure.

SymptomCauseWay back
400 rather than 200, usually after a redeploy, node up and correctly named The host allowlist fell back to the machine FQDN Fix the derivation in the launch script and redeploy; a hand-set value fails again next deploy
No response at all from the new hostname Certificate still issuing, or the tailnet lacks HTTPS certificates Wait out the first minute, then enable HTTPS certificates
A -1 suffix on the name after docker restart The state directory is not persisted Not recorded — the recognition only
A check fails right after a mount is retired Not recorded Restore that mount and stop rather than retiring the next port; no restore command is recorded
