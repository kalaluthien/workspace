Workspace-to-board channels

Board never edits a file to change a ticket. An agent session never writes a backlog.md. Board never reads a pane's screen, so a session reports by writing the row and never by printing. The 3× channel above are the whole joint, and the three sections below take one channel each.

Ticket store doors

A door is one HTTP endpoint on board's server. There are 6× door in total: five write and one read. Every door answers at http://localhost:8300. A live probe of /api/health on 2026-08-21 answered {"ok":true,"version":77}.

doorwhat it meanscalled by
Write
POST /api/backlog-tickets file a new piece of work any session; ?validate=1 checks and writes nothing
PATCH /api/backlog-tickets/{id}/head change the marker, tags, labels, title a session releasing a row back to open; board's own repair pass
PATCH /api/backlog-tickets/{id}/body replace the body text a session refining a row
POST /api/backlog-tickets/{id}/claim take the working marker; refused if somebody holds it the owner's tap, and a session taking a row
DELETE /api/backlog-tickets/{id} close: the row is marked done and kept for ever the session that shipped the work
Read
GET /api/snapshot read every pool's rows and every live session the /clean sweep, and a session with no row named

The refusal has a reason the code states. The working marker carries a second field, the holder, and the head door cannot write it. A caller who reached the marker there would leave a row saying it is being worked with nobody working it: The claimed marker is refused for the same reason and a stronger one. It is the one marker that carries a second field — the holder — and this door has no way to write it. board/src/board/server/tickets.py:263-278 @ c166ae3

The settled marker has the mirror rule. Session launch by board

This is the argument list the bridge builds at step 4. The prompt argument sits ahead of --allowedTools, whose value list is variadic and would otherwise swallow it as one more tool name.

argv = [
    "--session-id", launch.session_id,
    "--model", route.tier.model,
    "--effort", effort,
    launch_prompt,
    "--allowedTools", *settings.allowed_tools, *route.tier.extra_tools,
]

The prompt is a file rather than the argument itself, and the reason is a pair of limits. Typed text goes through the pane's line discipline, which discards a line past 1024 bytes and reports nothing. A launch argument goes through herdr, which refuses any argument holding a Unicode control character, and a forty-line template's own line breaks are exactly that. So the launch argument is one short line naming the file: board/src/board/bridge/delivery.py:1-25 @ c166ae3

Board does not tell the session how to do the work. It hands over the doors and the row's own words: Moving a ticket to working means "start this work", so the session is not told how to do it — it is handed the doors its tickets answer at and their own text, and the skill named on that line owns everything after. board/src/board/bridge/prompt.py:592-598 @ c166ae3

Session names

The double dash is the boundary. head_of() returns the part in front of it, and its own docstring states the role: This is the whole join. The store's claimed_by holds exactly this string for the row being worked, so the sweep, the liveness readout and cancel all read one value rather than three derivations of one. board/src/board/bridge/herdr.py:222-236 @ c166ae3

A worker the orchestrator launches keeps the same holder in front of its own name. That is what makes a worker reachable from outside its own session, because cancel reaches every pane in the namespace. Scenarios by first move

The confirmation clause tells the session to judge which kind of answer the row was waiting for 
— The owner tapped Start on this row themselves, so the tap is theirs. A tap can confirm, and it cannot decide: this board offers no way to express a choice, so never read it as picking one. Read the row and the proposal it points to, and judge what #need-you was waiting for. If it was a confirmation — the proposal states one recommendation and only acceptance was owed — the tap is that acceptance, exactly as written; anything they wanted changed is already in the row's own text above. Record the acceptance in that proposal document, then carry out the work the row asks for. If it was a decision — a choice among options, or an input only the owner can give — the tap does not carry it: ask the owner with the AskUserQuestion tool, offering the proposal's own options with its recommendation first.

Deliberate absences

  • No shared database. Neither side opens the other's store.
  • No file anywhere holds a ticket. Every pool moved into the store on 2026-08-19, and a backlog.md written back draws no card on any surface.
  • Board never reads a pane's screen, so a session's only report channel is the row.
  • Board never decides how the work is done. It hands over the doors and the row's own words.
  • A run has no claim, so nothing reconciles it and nothing sweeps its pane.
