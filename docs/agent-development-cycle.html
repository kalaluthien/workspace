One checked chain from use case to test

Every behaviour in a program-building entry becomes one checked chain: a use case, its scenario rows, and the test method that settles each row.

Five fixed directory names hold the chain. Four entrypoints run it. A machine reads every link in it.

Garden is the testbed. Camera adopts next, on the same stack. Board adopts with its own tools. The notes entry and the Jekyll site stay out of scope. The workspace root keeps its own arrangement. This proposal does not edit the docs contract. docs/README.md:49-83 @ 8c58061

Domain

The cycle moves four words around. Each one gets a fixed meaning below. The set is complete at 4× stage.

  • Spec — the normative .md text that states what the program must do. Every sentence in it is a predicate, a generating rule, or a decision with its reason. A spec is not a view. A view is the derived .html page that goes stale. A spec is not a description of what the code already does. A spec is not a commit gate, because no check in this cycle demands a spec edit. docs/templates/spec.md:9-13 @ 8c58061
  • Code — the program a machine runs, plus the configuration it reads. Code is not evidence that a spec is true. Code does not record a design decision, because a reader cannot tell a decision from an accident there.
  • Test — an executable check that settles one scenario row with a pass or a fail. A red test blocks the commit. A test is not a design check, because a test needs the code to exist first. A test is not a measure of quality.
  • Eval — a measurement of quality that informs and never blocks. It is a static metric, or a rubric judged with quoted evidence. An eval is not a gate. An eval is not a proof. A person still reads its verdict.

Options for a machine-checked spec

Three axes judge the four candidates. Can the option refute a design before code exists? What does the option cost to keep true? Does a patch that skips the spec break the option?

Key for the four panels: circled numeral — one option; dashed box — an artifact no entry holds at garden cdaf951; dashed arrow — a proposed link. Every option is unbuilt, so every panel is dashed. The verdict on each option is the paragraph that carries its numeral.

  1. Alloy everywhere — a model per artifact, checked on every commit. It refutes early. It gives up a bounded maintenance cost, because the corpus becomes a second description of every artifact. AWS rejected Alloy in 2015 on reach, after failing to represent rich data structures. Killed on reach and on drift. notes/wiki/alloy-specification-language.md:274-282 @ 9e2a365
  2. Markdown and scripts — identifiers in Markdown, and a few dozen lines of Python per rule. It survives a code-first patch, because its checks are syntactic. It gives up any design check, so a wrong relational shape reaches code unchallenged. Killed on the defect class it cannot catch. Its identifiers and its link checks survive inside option 3.
  3. Structured shell with attached models — one spec/ directory, four entrypoints, two gates. A model is optional, small, and attached to one use case. It gives up spec-first as a hard rule. Recommended.
  4. Kotlin reference model — a reference implementation in the test tree, run against the real code. It gives up early refutation, because it needs the code to exist. Absorbed rather than killed: it is a strong instrument at the test stage.
Alloy lost twice inside Amazon, which is why no option keeps a model corpus
  • Reach, 2015. AWS found no practical way to represent rich data structures in Alloy. Alloy 6 closes the temporal half of that gap and leaves the rest. notes/wiki/alloy-specification-language.md:274-284 @ 9e2a365
  • Maintenance, 2021. The ShardStore team at Amazon S3 wrote early models in Alloy and dropped them. They moved the reference model into Rust after discussing long-term maintenance. notes/wiki/alloy-specification-language.md:287-297 @ 9e2a365
  • The recorded verdict. Alloy does “not earn its cost as a maintained CI artifact: the model is a second description of the code and drifts like one.” It pays where the structure is relational and the failure is a shape nobody would think to test. notes/wiki/alloy-specification-language.md:270-345 @ 9e2a365
  • Much of the value sits in the writing. Jackson found that “a high proportion of the flaws were detected before the tools were even run.” notes/wiki/alloy-specification-language.md:347-350 @ 9e2a365

Structured shell with attached models

This option refutes a relational design before code exists. It keeps the model corpus small, because a model attaches to one use case and never to an artifact. That shape is what the recorded evidence allows.

Two later observations reverse the choice. First, no model refutes a design garden would have shipped. This option then collapses into option 2. Second, the model corpus outgrows the use cases paying for it. The ShardStore reason then kills it.

Three recorded findings bound what the eval stage may claim.

  • The judged code is model-written. The available judges share its model family, so self-preference bias is live. notes/wiki/code-simplicity-metrics.md:105-109 @ 9e2a365
  • A judge answers a binary checklist. It quotes its evidence for every failure. notes/wiki/code-simplicity-metrics.md:110-118 @ 9e2a365
  • Agreement with humans on constraint satisfaction runs 13–39 percent, so a judge gates nothing and counts nothing. notes/wiki/code-simplicity-metrics.md:119-125 @ 9e2a365

The second mitigation is a person: the owner spot-checks a judged sample.

Scenario row

A use case borrows its unit from concept design: a reusable unit of user-facing behaviour with a purpose of its own. notes/wiki/concept-design.md:33-56 @ 9e2a365

A settling reference takes one of three forms: a test method, a rubric name, or the word manual with its reason. A model stays optional. Registering a plant and the home-screen widget stay prose-only use cases with no model.

Both gates are deterministic and run in seconds, so they chain into the hook the entry already has. The lint compiles the file, because a comment fools a text search. The ban on integers removes Alloy's silent overflow trap by construction. An Analyzer run happens when the design is worked, and never on a commit.

One limit has no mechanical cover. A behaviour change that no test observed stays invisible to every check above. The chain then stays green while the spec is wrong. The eval stage and the owner's own read cover it.

Recovery after a code-first patch

No gate above demands a spec edit, so a hotfix lands. Code and tests move. The change gates on build and tests as always. What lags appears on the staleness list. An agent then runs three steps cold.

  1. Read the flagged spec's scenario rows. The staleness report names the spec.
  2. Diff the code since the spec's verified date.
  3. Rewrite the predicates and the rows to match. The tests still carry their sc- identifiers, so the chain survives the patch.

Spec-first stays the preference. It is a warning from a check. It becomes a gate only after it catches something.

Model evidence

One model was written and run on 2026-08-15. It states garden's pinned-interval rule in 41 lines: only the owner ever changes a pinned plant. Its assertion is anchored on the use case's declared name, so the Alloy compiler sees the link.

The check was made red twice and green again. The first mutation disabled the frame fact, which proved the assertion reads the transition system at all. The second mutation deleted the learner guard, which proved the assertion reads the right part of it. Two earlier attempts could never be made red. No text search would have found either one.

The rule this buys: a model's check earns trust only after it has been observed red twice. Both mutations and both results sit beside the model. A settling test obeys the same fail-first rule.

Five runs, the anchored assertion, and the 41-line model in full
  1. Baseline check — nothing changed, UNSAT. No counterexample within 4 objects and 1 to 8 steps.
  2. Baseline run — nothing changed, SAT. A pinned plant is reachable, so the model is not vacuous.
  3. First mutation — the frame fact disabled, SAT. The assertion reads the transition system.
  4. Second mutation — the learner guard deleted, SAT. The assertion reads the design rule it exists to protect.
  5. Restored — both mutations undone, UNSAT. The mutations caused the red, and not the model.

A bare java -jar alloy.jar opens the Analyzer window and blocks forever, with no output and no error. Pass the exec subcommand and the headless flag, and read the SAT or UNSAT line rather than the exit code, which is 0 either way.

"$JAVA_HOME/bin/java" -Djava.awt.headless=true -jar alloy.jar exec -f -c 'uc_pin_interval' interval.als
// uc-pin-interval — the owner types an interval; nothing in the app may move it.
// A design check: run when this design changes, recorded, never a commit gate.

sig Days {}
enum Actor { Owner, Learner }
one sig Trail { var actor: lone Actor }   // who acted this step; none on stutter

sig Plant {
  var pinned: lone Days,   // the interval the owner typed
  var learned: lone Days   // the learner's current target
}

pred ownerPins[p: Plant, d: Days] {
  Trail.actor' = Owner
  p.pinned' = d
  p.learned' = none        // an owner edit resets the learner
  all q: Plant - p | unchanged[q]
}
pred learnerAdjusts[p: Plant, d: Days] {
  no p.pinned              // the learner may act only on an unpinned plant
  Trail.actor' = Learner
  p.learned' = d
  p.pinned' = p.pinned
  all q: Plant - p | unchanged[q]
}
pred unchanged[p: Plant] { p.pinned' = p.pinned and p.learned' = p.learned }
pred stutter { no Trail.actor' and all p: Plant | unchanged[p] }

fact events {
  always (stutter
    or (some p: Plant, d: Days | ownerPins[p, d] or learnerAdjusts[p, d]))
}

// The guarantee: only the owner ever changes a pinned plant.
assert uc_pin_interval {
  always all p: Plant |
    (some p.pinned and not unchanged[p]) implies Trail.actor' = Owner
}
check uc_pin_interval for 4 but 1..8 steps

run somePinnedTrace { eventually some p: Plant | some p.pinned } for 4 but 1..8 steps
