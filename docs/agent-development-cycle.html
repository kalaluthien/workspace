Question
What fixed directory contract and work cycle should agent sessions follow to develop a workspace project that builds a program, so the specification is one machine-checkable source of truth that survives code-first patches?
Updated
2026-08-15
Commit
8fd13c1

Garden’s 14 specs are prose that nothing refutes, and their one link to the tests names a whole test class, so no machine ever sees the drift; make every behaviour one checked chain instead — a use case, its scenario rows, and each row’s settling test method.

Answer

Conclusion
  1. 1Contract. Five fixed directory names — README.md, spec/, docs/, scripts/, hooks/ — and four entrypoints: spec, code, test, eval. Everything else stays the framework’s.
  2. 2Chain. One concept carries consistency: a use case, its scenario rows, and each row’s settling check, named method by method, with the test carrying the row’s id back.
  3. 3Checks. Two checks gate a commit (resolution, model lint) and three only inform (staleness, vocabulary, Analyzer runs). A green licenses resolution and nothing more.
  4. 4Code first. No gate needs a spec edit, so a hotfix lands. The staleness list is the recovery worklist, and recovery is three steps an agent runs cold.
  5. 5Models. An Alloy model is optional evidence attached to one use case. It never gates, and it is trusted only after it has been made red twice.

Options

Conclusion
  1. 1Axes. Three, named before any option is judged: can it refute a design before code exists; what does it cost to keep true; does an unspecced patch break it.
  2. 2Winner. The structured shell with attached models — the only option that refutes early without maintaining a second description of the whole system.
  3. 3Losers. One is killed on reach, one on the defect class it cannot catch, and one is absorbed rather than killed: it needs code, so it belongs at the test stage.

The tool lost twice at AWS, and that is why no option keeps a model corpus
  • Expressiveness, 2015. AWS rejected Alloy because it could find no practical way to represent rich data structures; Alloy 6 closes only the temporal half of that gap.
  • Maintainability, 2021. S3’s ShardStore team wrote early models in Alloy and dropped them once they discussed long-term maintenance, moving the reference model into Rust.
  • The recorded verdict, quoted. Alloy “does not earn its cost as a maintained CI artifact: the model is a second description of the code and drifts like one.” It pays where the structure is relational and the failure is a shape you would not think to test.
  • Much of the value is in the writing. Jackson’s own finding: “a high proportion of the flaws were detected before the tools were even run.” A separate controlled study (n=30) found writers at all levels struggled to write a model from scratch.
  • Source. notes/wiki/alloy-specification-language.md lines 270–350 (notes 9e2a365).
Judges inform and never gate: agreement on rule-following runs 13–39%
  • The validated method is a binary checklist with quoted evidence per answer, not a 1–10 score.
  • The measured ceiling. Agreement with humans on constraint satisfaction runs 13–39% depending on the judge, and no judge should be asked to count anything.
  • The same page draws this design’s boundary: script the cross-checks, model-check the one genuine state machine as a design check, prove nothing.
  • Source. notes/wiki/code-simplicity-metrics.md lines 86–180 (notes 9e2a365).

Recommendation

Conclusion
  1. 1Why it wins. It is the only option that can refute a design before code exists while keeping models optional, small, and attached to single use cases — the shape the recorded evidence allows.
  2. 2Flip condition. Each loser’s kill reason is what holds this up. If no model ever refutes a design garden would have shipped, the design collapses to markdown and scripts; if the model corpus outgrows the use cases that pay, the ShardStore reason kills it.
  3. 3Accepting costs one commit. A workspace spec, docs/agent-development-cycle.md, records the decision and carries the machine contract the scripts/spec implementations parse.

Chain

One concept answers consistency: a use case, its scenario rows, and each row’s settling check.

  • A use case is a shell entry uc-<kebab-name> with a one-line purpose and its predicates in prose. The unit is borrowed from concept design (notes/wiki/concept-design.md, notes 9e2a365).
  • A scenario row lives in the document it belongs to, so acceptance sections stay where they are and no second central table appears.
  • The row names a method, not a class, because the class-level link measured meaningless above.
  • The settling test carries the sc- id at its own end, in its name or a comment.
  • A model is optional. Registering a plant and the widget stay prose-only use cases with no model, and that is normal.
- sc-<kebab-name> (uc-<name>) — settled by <TestClass#method | rubric-<name> | manual(reason)>

  • The lint compiles the file. A grep alone can be fooled; the ban on integers kills Alloy’s silent overflow trap by construction, and day arithmetic belongs in Kotlin tests.
  • Analyzer runs happen when the design is worked, never per commit.
warning A behaviour change that no test observed is invisible to every mechanical check here.
  • Consequence: the chain stays green while the spec is wrong.
  • Avoidance: the eval stage and the owner’s own read. The staleness list only sees files a settling test touched.

Recovery

No gate above requires a spec edit, so a code-first patch lands: code and tests move, and the change gates on build and tests as always. What lags appears on the staleness list, and recovery is three steps an agent runs cold.

  1. Read the flagged spec’s scenario rows. The staleness report names the spec.
  2. Diff the code since the spec’s Last verified date.
  3. Rewrite the predicates and the rows to match. The tests still carry their sc- ids, so the chain survives the patch.

Spec-first stays the preference. It is a check’s warning, promoted to a hook only after it catches something.

The whole 41-line model, quoted so this document carries its own evidence 
// uc-pin-interval — the owner types an interval; nothing in the app may move it.
// A design check: run when this design changes, recorded, never a commit gate.

sig Days {}
enum Actor { Owner, Learner }
one sig Trail { var actor: lone Actor }   // who acted this step; none on stutter

sig Plant {
  var pinned: lone Days,   // the interval the owner typed
  var learned: lone Days   // the learner's current target
}

pred ownerPins[p: Plant, d: Days] {
  Trail.actor' = Owner
  p.pinned' = d
  p.learned' = none        // an owner edit resets the learner
  all q: Plant - p | unchanged[q]
}
pred learnerAdjusts[p: Plant, d: Days] {
  no p.pinned              // the learner may act only on an unpinned plant
  Trail.actor' = Learner
  p.learned' = d
  p.pinned' = p.pinned
  all q: Plant - p | unchanged[q]
}
pred unchanged[p: Plant] { p.pinned' = p.pinned and p.learned' = p.learned }
pred stutter { no Trail.actor' and all p: Plant | unchanged[p] }

fact events {
  always (stutter
    or (some p: Plant, d: Days | ownerPins[p, d] or learnerAdjusts[p, d]))
}

// The guarantee: only the owner ever changes a pinned plant.
assert uc_pin_interval {
  always all p: Plant |
    (some p.pinned and not unchanged[p]) implies Trail.actor' = Owner
}
