Answer

A memory file's kind comes from one question — what would make this file wrong — and the three answers to that question are the whole taxonomy.

Conclusion

1Falsifier. The one axis: what would make this file wrong.

2Episodic. Nothing falsifies what already happened, so history- is append-only.

3Semantic. backlog and profile- assert a state the world can move, so both are updated in place.

4Procedural. setup-, feedback- and pitfalls say how to act, so all three are deleted when the tool is gone.

Discriminators

Conclusion

1Work or owner. Semantic splits on what the file is about: live work, or the owner.

2Cost of loss. setup- and feedback- split on what losing the file costs: a probe, or a repeated failure.

3Reach. pitfalls takes what does not generalize — one project's own traps, in one file per pool.

MemtypeHoldsLifecycle
history-what version control cannot see: unversioned changes, rejected options and their kill reasonsextended, never rewritten
backlogthe pool's live work, one file per poolan item is deleted when it closes; no done marker
profile-a standing owner preferencerewritten when the preference changes
setup-one tool's or environment's own factsdeleted when the tool or fact is gone
feedback-a rule bought with an observed failuredeleted when the practice is gone
pitfallsone project's debugging traps, in its own technology or conventions; one file per poolan entry is deleted when its technology is gone
Each lifecycle follows from its own discriminator, not from a house style
  • backlog holds live work, so closing the work deletes the item; profile- holds a preference, so a change only rewrites a line.
  • A setup- fact is re-derivable by probing the tool, so losing one costs a probe.
  • A feedback- rule was bought with an observed failure and cannot be re-derived, so losing one repeats the failure.
  • pitfalls and feedback- are both bought with a failure, and generality tells them apart: a trap tied to one project's technology stays in that pool's single pitfalls.md, while a rule that travels earns its own feedback-<topic> file (~/.claude/agents/debugger.md §Filing).
  • A fixed filename is not a memtype signal: backlog and pitfalls both take exactly one file per pool, yet sit in different classes.

Omissions

  • The pin's reach — the Commit field pins both repositories this view reads. The pools themselves are version-controlled nowhere (~/.claude/.gitignore ignores projects/), and several sessions write them at once, so every count here is one walk's snapshot. What the view claims is the structure — six prefixes in three classes — not the totals.
  • File contents — what each memtype holds, never what any file says.
  • Pool routes — the sibling view agent-config-scopes.html owns the scope-to-pool mapping.
  • Item grammar — the marker, tag, and date form inside a backlog.md belongs to the pool contract.
  • Enforcement — no installed hook pairs a prefix with its metadata.type (re-checked over ~/.claude/hooks/ and ~/workspace/hooks/), so the census is a walk, not a guarantee — the four declarations this walk caught are what that missing check lets through.
