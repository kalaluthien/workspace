Answer

One file holds the rules, one template per doctype holds that doctype's contract and its checklist, and five components hold one page part each as working markup — the writer reads them in that order, fills the template, scores the checklist, and hands the file back.

Conclusion

1Request. The caller names the doctype, the target path and the sources. The writer chooses none of the three.

2Read. The writer reads the constitution, then that doctype's template, then the components the template names, then the sources.

3Fill. The writer copies the template to the path, pastes the component markup in, deletes every template comment, and pins the commit it read the sources at.

4Check. The writer scores the template's own rubric and fixes each failure. The file and the report go back; the caller commits.

Constitution

Conclusion

1One file, five sections. System, Procedure, Style, Guardrails, Report — each holds one kind of rule, and nothing else is normative.

2Style is most of it. 137 of the file's 255 lines say how the page reads; the other four sections share the rest.

3It breaks ties. Where a template rule and this file disagree, this file wins and the writer names the override in its report.

SectionLinesThe kind of rule it holds
System17–75what a document is: the two kinds, the three doctypes, the header fields, naming and catalogue
Procedure77–98the four ordered steps of one render, drawn as the path figure
Style100–236how the page reads: language, structure, colour, figures, citing — five sub-sections
Guardrails238–248four prohibitions that hold whatever the doctype
Report250–255what the writer's final message carries, and that it carries nothing else
  • Nothing is written that cannot be checked. Step 3 of the procedure: "What you cannot verify, you do not write — name it as not shown, or ask the caller in your report" (document-writer.md:92–94).
  • The writer never decides. Guardrails opens with "Decide nothing. A decision you find unrecorded is reported back, never written into the view" (document-writer.md:240–241).
  • Style leads with one ground rule. "keep the document short, and separate the crucial from the detail — obsessively" (document-writer.md:113–114); the rest of the section serves it.
  • Every other site holds a pointer. A repository's docs/README.md keeps only its machine contract and a link here (document-writer.md:11–15).
Why the rules sit in the agent's own file, and not in a docs README

A rule lives in the single file its actor loads at the moment the rule binds. The writer is the only actor that touches every view in every repository, and its own definition is the file it always loads (owner decision, 2026-08-04, docs/agent-document-system.md).

Before it, seven sites stated the rules, and the drift showed in the tree rather than in an argument: one entry's template copy named a different filename grammar than its parent, and another's said "when the two disagree, the parent wins", which names the drift without preventing it.

Two arrangements lost. A docs/README.md master lost on locality, because the writer needs the rules inside its own definition to act on them. Making the writer the sole author of every document lost because the agent doing the work writes the spec, in the same change as what the spec governs.

The accepted cost: the constitution lives in ~/.claude while the documents it governs live in the repositories, so no single commit changes a rule and the documents that follow it.

Templates

Conclusion

1A comment, then a page. Every template opens with one long comment — notes, contract, rubric — and the page skeleton follows it.

2The rubric ships with the shape. The checklist sits in that comment, so writer and reviewer score the same list.

3Four files, one filled. Three view templates, plus spec.md, which the writer never fills.

  1. notes — band. What this doctype adds and nothing the constitution already says: "this file adds only what is particular to this doctype" (explanation.html:3–5). Line 21 is one row of the table that picks the lead figure from the question's level — six levels, six different figures owed.
  2. contract — band. Three required- lines: the header fields, the sections, and the elements the finished document must carry.
  3. rubric — band. The scored checklist: "the writer checks every item before delivering and reports the result; the reviewer scores against the same list. Binary, no partial credit" (explanation.html:42–44).
  4. styles — band. The inline CSS, already copied from the components, so the finished page needs no other file.
  5. skeleton — band. The page to fill: header fields, lead figure, elements table, sections, sources footer. Every comment inside it is deleted at render.

  • The reader's question picks the template. How does it work → explanation; how do I do it → guide; what should change → proposal (document-writer.md:38–42).
  • Every view carries a question line. That is the Question field, or a guide's Goal. A view without one lists with a blank line on the reading surfaces (observed 2026-08-07, board).
  • The fourth template is not a doctype. spec.md is the one specification template. It offers five section shapes — decision, rule, procedure, capability, ledger — and the agent doing the work fills it, in the same change as what the spec governs.
  • No template carries a Reviewed term. The writer fills the header from the template, so a re-render leaves the page reading as never reviewed. That is the intent, not a defect.
Why a re-render un-reviews the page

The Reviewed date says when somebody last read the document against the tree and found it still true. A re-render replaces the prose, so a review of the old prose no longer vouches for anything (owner, 2026-08-12).

The term is declared in the docs contract, ~/workspace/docs/README.md, where a reader parses it. A view without it is valid everywhere: it means never reviewed, not missing.

Components

Conclusion

1Five parts, one file each. Base, provenance, callout, figure, disclosure — one page part per file.

2Each file is its own example. The page it renders obeys the rules it states, so the writer copies markup that already works.

3Copied, never linked. The markup is pasted into the document, so the finished page opens on its own from file://.

  1. rules — band. What the part is and what it enforces, in prose: "This file demonstrates itself: its own <style> block is the component" (base.html:3–4).
  2. marked css — band. The style the writer copies. The two /* component: … */ markers say where the copy starts and stops, so nothing around them travels with it.
  3. self demo — band. A working page built from the part, so every rule above it has a visible instance on the same screen.

  • The components carry the rules the constitution only numbers. The 10-unit label floor and the 360-unit pan threshold are stated in the constitution; the arithmetic behind them is in figure.html:34–41.
  • A component can hold a trap the writer would not guess. "Suffix every id (arrow-<diagram>, not arrow) — inline SVG shares one id namespace with the whole page" (figure.html:99–101).
  • Disclosure has one law of use. "Default closed. A block worth opening by default is body content" (disclosure.html:21).

Omissions

  • The rubric items are counted, not listed. The table gives each template's item count; what a single item asks is not on this page.
  • The style rules are located, not quoted. The Constitution table says which section fixes language, colour and figures. It does not say what those rules require.
  • The spec side stops at the template. The five spec section shapes are named; how to fill one is out of scope.
  • Two trees back this page. The constitution, templates and components sit in ~/.claude at e19479b; docs/ sits in the workspace worktree at 803540c.
  • One tree was dirty elsewhere. Every source of this document was clean at render time. Around them, ~/.claude carried edits to its own CLAUDE.md and settings.json and an untracked hook script; the workspace worktree was clean.
