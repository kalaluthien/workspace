Answer

The caller names the doctype, the path and the sources; the writer fills that doctype's template, checks it against the template's own rubric, and hands the file back with a report for the caller to commit.

Conclusion

1Request. The caller names the doctype, the target path and the sources. The writer chooses none of the three.

2Render. The writer fills the template from the components and the sources, and pins the commit it read them at.

3Rubric check. The writer walks the template's rubric item by item and fixes every failure before delivery.

4Delivery. Two things come back: the file and the rubric report. The writer runs no git command.

Parts

Conclusion

1One rule file. ~/.claude/agents/document-writer.md is the only normative site. Every other place holds a pointer to it plus the machine contract its own tools read.

2Shapes beside it. templates/ holds one file per doctype and components/ holds five page parts, both under ~/.claude/agents/document-writer/.

3Copied, never linked. A component is pasted into the document, so the finished page opens on its own from file://.

  • A template carries its own rubric. The checklist sits in the template's opening comment, so the writer and a later reviewer score the same list.
  • The constitution wins a tie. Where a template rule and the constitution disagree, the constitution holds, and the writer names the override in its report.
  • Each component is its own example. The file demonstrates the rules it states, so the writer copies working markup rather than reading a description of it.

Why the rules sit in the agent's own file, and not in a docs README

A rule lives in the single file its actor loads at the moment the rule binds. The writer is the only actor that touches every view in every repository, and its own definition is the file it always loads (owner decision, 2026-08-04, docs/agent-document-system.md).

Before it, seven sites stated the rules, and the drift showed up in the tree rather than in an argument: one entry's template copy named a different filename grammar than its parent, and another's said "when the two disagree, the parent wins", which names the drift without preventing it.

Two arrangements lost. A docs/README.md master lost on locality, because the writer needs the rules inside its own definition to act on them. Making the writer the sole author of every document lost because the agent doing the work writes the spec, in the same change as what the spec governs.

The accepted cost: the constitution lives in ~/.claude while the documents it governs live in the repositories, so no single commit changes a rule and the documents that follow it.

Kinds

Conclusion

1Two kinds. .md is a specification and .html is a view: the extension is the kind.

2Views only. The writer renders views. The agent doing the work writes the spec, in the same change as what the spec governs.

3A view decides nothing. A view only shows a decision a spec already records, written in the same change.

Doctypes

Conclusion

1Three shapes. The reader's question picks one: explanation, guide or proposal.

2One question each. A document that answers two questions is two documents.

3Only a proposal may describe what does not exist. An explanation and a guide make claims the repository can settle, and a claim it cannot settle is a defect in them.

DoctypeThe reader's questionHeader fields it addsTemplate
explanation how does it work, why is it this way, what shape does it have, what did we find Question explanation.html

proposal what should change, and to what Status, Question proposal.html
  • Every view carries a question line. That is the Question field, or a guide's Goal. The reading surfaces draw it under the title, and a view without one lists with a blank line (observed 2026-08-07, board).
  • The fourth template is not a doctype. templates/spec.md is the one specification template, and the writer does not fill it.

Handover

Conclusion

1Delivery is a message. The writer leaves the file and the rubric report, and runs no git command.

2The catalogue moves with the document. The caller edits INDEX.md in the same commit as the document.

3A re-render un-reviews the page. The writer never writes a Reviewed date, and never carries an old one over.

Why a re-render leaves the page reading as never reviewed

The Reviewed date says when somebody last read the document against the tree and found it still true. A re-render replaces the prose, so a review of the old prose no longer vouches for anything.

The mechanism matches the rule by itself: the writer fills the header from its template, and no template carries a Reviewed term. The docs contract, ~/workspace/docs/README.md, declares the term, and a reader parses it there (owner, 2026-08-12).

Omissions

  • The style rules stay in the constitution. It also fixes the language, the colour and the figure forms of a view. The path figure shows where those rules apply, not what they say.
  • The rubric keeps its own items. Stage 3 shows that a check happens, not what the check covers.
  • The spec side is named, not walked. Who writes a spec is in Kinds; the section shapes inside templates/spec.md are out of scope here.
  • Two trees back this page. The Commit field pins both. The constitution, templates and components sit in ~/.claude at e19479b; docs/ sits in the workspace worktree at 26b5274.
  • Both trees were dirty elsewhere. Every source of this document was clean at render time. Around them, ~/.claude carried edits to its own CLAUDE.md, settings and hooks, and the workspace worktree carried the in-flight change that retires the old proposal.
