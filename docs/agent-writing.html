Context inside the fork

The skill runs in a fork of its own. The frontmatter pins the model to opus. background: false holds the invoking turn until the fork returns. allowed-tools grants Read, Grep, Glob, Write, Edit, and Bash. .claude/skills/writing/SKILL.md:1-10 @ 1c7bffb

The fork holds no conversation history. No user answers a question during the run. Every claim on the page comes from a file the run read. Memory is not a source. Only the return message reaches the main session. Every file read and all tool output die with the fork context. .claude/skills/writing/SKILL.md:28-39 @ 1c7bffb

The return message carries a status line and five sections.

  • ## Output — the absolute output path, then the section list.
  • ## Findings the reader needs — 3 to 6 facts, each with the file it came from.
  • ## Grounding — every file the run read. It is a superset of every file the message names elsewhere.
  • ## Residual uncertainty — the highest-risk claim on the page, and what would settle it.
  • ## Next action — the caller's work: the INDEX.md line, and the commit that lands both files.

Brief naming a readable path

The run reads the file. It pins that file's repository with git rev-parse --short HEAD. Each citation carries the file, the line, and the commit of the repository the file sits in.

Brief naming no readable source

The run ends. It returns STATUS: INSUFFICIENT-INPUT, names what is missing, and writes no HTML. A proposal brief takes no exemption here, because its AS-IS half still needs a readable source.

Run sequence, brief to delivered file

Nine steps make one run, in four stages.

An explanation and a proposal each hold one section of negative space: what does not start the subject, and what the subject does not change. Rule L asks for the fewest components. It never trims that section. .claude/skills/writing/references/draft-rules.md:135-146 @ 1c7bffb

Render check of the built page

Step 7 calls the script by its installed path, because the fork inherits the caller's working directory. Headless Chrome on macOS does not lay out below 500 CSS units. The script measures the width it received with window.innerWidth and prints it beside each render. A narrow render that reads as text cut off at the right edge is the instrument, not the page. .claude/skills/writing/scripts/render-check:19-26 @ 1c7bffb

check-figures holds three rules, and a figure passes all three.

  • Annotation text is at least 10 viewBox units, which renders above the 8 px floor on a phone.
  • A figure over 360 viewBox units carries class="pan" and an inline min-width equal to its viewBox width.
  • A figure viewBox is at most 620 units wide, the desktop measure.

The run then reads both images back. A label that touches another mark is invisible to the script, which reads markup only. ~/.claude/git-hooks/check-figures:26-28 @ 98af604
